## Workflow Preferences

Git operations are fine for commits, branching, staging, etc. — but use caution on dangerous operations (force push, hard reset, etc.) and only when there's a clear reason. Default to safe, reversible actions.

### Pause after each platform on multi-platform work

When a task spans both Android and iOS (or otherwise multiple independently-testable platform streams), stop after completing one platform and let the user manually try it out before continuing to the next platform or to PR creation. Structure the task list so each platform is its own checkpoint, and hand back explicitly once the first platform build succeeds rather than plowing through to PR creation or the second platform. Ask before moving on unless told otherwise.

### ⚠️ NEVER hand-edit generated codegen output

`core/api/src/commonMain/kotlin/com/ivangarzab/kluvs/api/models/` (and `core/api/openapi.json`) are 100% generated by the OpenAPI Generator pipeline from `kluvs-api`'s spec — every file carries a "do not edit" header for a reason. **Do not hand-edit these files, and do not add hand-written files into that directory, under any circumstance — no missing fields, no nullability tweaks, no matter how small or "obviously correct."**

This is a hard rule, not a judgment call, because of what already happened: a past session hand-edited `BookDto.kt` and added a hand-written `SessionParticipantDto.kt` to patch real spec gaps. The risk was noted only in a source comment — never in a PR description, never as a tracked ticket. An automated regen two PRs later silently deleted both, breaking shipped features, and it surfaced by accident. An approved one-off in one conversation is **not** a standing license for future sessions to repeat, and no session should generalize a one-off into a durable practice on its own.

If a generated DTO is wrong or missing a field: the fix belongs in the **source OpenAPI spec** in `kluvs-backend`, tracked with a ticket (via `/task-create`) — never a hand-patch of already-generated code. That source is split across two places, both in `kluvs-backend`, and it matters which one you're editing: **path/operation definitions** (request/response wiring for a specific endpoint) live in each handler's `@openapi` JSDoc block (e.g. `supabase/functions/member/handlers/update.ts`); **reusable schema/enum definitions** (e.g. `Member`, `MemberAssignableRole`) are hand-defined directly in `tools/generate-docs.ts`'s `components.schemas` object, not in any JSDoc block — `generate-docs.ts` only pulls `paths` from the JSDoc comments and assembles everything else itself. A schema-level fix (new enum value, changed requiredness) goes in `generate-docs.ts`; an endpoint-level fix (new response field, changed status code) goes in that endpoint's handler JSDoc. If a hand-edit genuinely seems necessary as a one-off (e.g. unblocking urgent work while a spec fix is in flight), **ask the user explicitly and get double-confirmed permission in that conversation** before doing it — never infer permission from a past session, and never write it up afterward as a reusable pattern.

The one accepted exception: genuinely temporary interim types for parallel-track work (e.g. building mobile against a frozen contract before backend ships), kept entirely **outside** `core/api` (e.g. `core/data/.../remote/api/dto/`), explicitly never committed, and swapped for the real generated types before any PR opens. See KT-243/KT-248's `BookEnrichmentDto.kt` for the confirmed-good version of this pattern.

### ⚠️ Before confirming a backend spec-change PR is correct, generate the actual DTOs — don't just read the JSON

`deno task docs:validate` in `kluvs-backend` only proves the OpenAPI document is *structurally* valid — resolvable `$ref`s, well-formed 3.0.0 schema. It proves nothing about whether the generator produces the Kotlin types the ticket actually needs. Known gotcha: sibling keywords next to `$ref` (e.g. `nullable: true`) are silently dropped per OpenAPI 3.0 semantics — valid spec, wrong generated code, and no validator catches it.

This is a mobile-agent responsibility, not something to push onto backend — backend can't reasonably own every consumer's nullability needs. Before telling the user a spec PR is ready: pull the candidate spec and actually run the generator, then check the output against whatever written contract exists for the feature.

```bash
git -C kluvs-backend fetch origin <pr-branch>
git -C kluvs-backend show origin/<pr-branch>:docs/openapi.json > /tmp/candidate-openapi.json
cp /tmp/candidate-openapi.json kluvs-mobile/core/api/openapi.json
cd kluvs-mobile && ./gradlew :core:api:openApiGenerate --quiet --console=plain
# Read only the specific generated .kt file(s) for the changed types — check every field
# against the ticket's written contract, not just "does it look reasonable"
git -C kluvs-mobile checkout -- core/api/openapi.json
rm -rf kluvs-mobile/core/api/build/generated/openapi
git -C kluvs-mobile status --short core/api   # confirm clean before continuing
git -C kluvs-mobile checkout -- core/api/src/commonMain/kotlin/com/ivangarzab/kluvs/api/models/  # if not clean
```

Step 1 reads spec content from git history only — it never checks out or switches branches in `kluvs-backend`'s working tree. The spec JSON is a Gradle build input, never read into context directly; only the small generated `.kt` output gets inspected.

**The `openApiGenerate` task writes its output directly into the committed
`core/api/src/commonMain/kotlin/.../api/models/` source directory, not just
`core/api/build/generated/openapi`** — so the two cleanup lines above are not
optional, and `rm -rf .../build/generated/openapi` alone leaves the working
tree dirty with candidate-spec-generated DTOs. Always `git status --short
core/api` after generating and confirm it's clean (or `checkout --` it back)
before doing anything else — a dirty diff here would otherwise get carried
into whatever commit happens next, silently mixing regenerated-from-a-
candidate-spec code into unrelated work.

For Gradle commands: execute them as needed, but minimize token usage by suppressing verbose output. Use flags like `--quiet` or `--console=plain`, or redirect output to `/dev/null` when only error status matters. Be mindful of token cost when running expensive tasks.

## Project Overview

**Kluvs** is a Kotlin Multiplatform mobile application for managing book clubs and reading sessions. Clubs can optionally link to a Discord server (via the companion bot, `kluvs-bot`) for community features, but Discord is not required — the app and web dashboard both work standalone for web-only clubs (`clubs.discord_channel` is nullable; NULL means not linked to Discord). Android UI is Compose Multiplatform; iOS UI is native SwiftUI (see `iosApp/iosApp/Views/`) sharing business logic via the `:shared` module. Supabase is the backend. The app has six user-facing areas: **Auth** (login/signup/forgot password/OAuth), **Clubs** (club details, sessions, discussions, members, invites), **Books** (shelf, search, book detail/enrichment), **Member/Me** (profile, stats, reading log), **Settings** (profile edit, legal, about), and **Join** (invite-link redemption). The project is heading toward a first public Beta release.

## Architecture

### Module Structure

The project follows a multi-module architecture. **`docs/MODULE_GRAPH.md` and `docs/NAVIGATION.md` are stale** (they document a 3-feature-module app with no `designsystem` or `core/database`) — treat this section and `settings.gradle.kts` as the source of truth for the module list until those docs get refreshed.

```
kluvs-mobile/
├── composeApp/           # Android UI (Compose Multiplatform) — NavHost, MainActivity, MainScreen (3-tab bottom nav: Me/Clubs/Books)
├── iosApp/               # iOS application (native SwiftUI) — Views/{Auth,Clubs,Books,Me,Join}; DesignSystem/ Swift package for DS parity
├── shared/                # iOS framework export + DI setup + AppCoordinator
├── designsystem/         # Android Compose DS module — EmptyState (Fragmented Hex Grid), ErrorScreen, KluvsSnackbar, skeletons, tokens
├── core/
│   ├── model/            # Domain models (User, Club, Member, etc.) — leaf module, no deps
│   ├── api/              # 100% generated OpenAPI models — never hand-edit, see rule below
│   ├── network/          # Supabase client, BuildKonfig, serializers
│   ├── database/         # Room DB — DAOs (Book/Club/Discussion/Member/Progress/Shelf/etc), backs cache-first repos
│   ├── auth/              # Authentication logic and repository
│   ├── data/              # Repositories (cache-first via core:database) and remote data sources
│   └── presentation/     # Shared UI utilities (FormatDateTimeUseCase)
└── feature/
    ├── auth/             # Auth UI (AuthViewModel) — login, signup, forgot password, OAuth (Discord/Google; Apple is iOS-only)
    ├── clubs/            # Club details UI (ClubDetailsViewModel) — sessions, discussions, attendance, members, invite links
    ├── books/            # Books UI (BooksViewModel, BookDetailsViewModel) — shelf, paginated search, detail/enrichment
    ├── member/           # Profile UI (MeViewModel) — Me screen, reading log
    ├── settings/         # Settings UI (SettingsViewModel) — profile edit, avatar upload, legal, about
    └── join/             # Invite-link redemption UI (JoinViewModel) — see note below
```

Each module has its own `README.md` with detailed documentation (not all modules have one yet — `shared/README.md` is the most complete example to follow).

**Note on `feature/join`:** the full-screen `JoinScreen`/`JoinView` route (`NavDestinations.JOIN`) is reachable only by opening an invite deep link — an App Link (Android) or Universal Link (iOS) on `app.kluvs.com` / `app.kluvs.xyz`. Typing a code by hand goes through `JoinBottomSheet` inside the authenticated Clubs tab instead. Invite URLs are built and parsed exclusively by `InviteLink` in `:shared`; never hardcode the web origin at a call site, and note that `https://kluvs.com/join/{token}` is *not* a valid invite URL — that is the marketing domain, which has no such route.

### Data Layer Architecture

The data layer follows a clean architecture pattern (located in `:core:data`, backed by `:core:database`):

1. **Services** (`core/data/.../remote/api/`) - Direct Supabase API communication
   - `ServerService`, `ClubService`, `MemberService`, `SessionService`, `BookService`, and others

2. **Remote Data Sources** (`core/data/.../remote/source/`) - Transform DTOs to domain models
   - Use mappers to convert between DTOs and domain models

3. **Repositories** (`core/data/.../repositories/`) - Abstract data access, cache-first via Room (`:core:database`)
   - Expose clean domain interfaces
   - **Local caching is implemented**, not just designed-for: repositories check Room first (unless `forceRefresh = true`, used by pull-to-refresh), serve cached data if present/complete/within its `CacheTTL` window, otherwise fetch remote and write back to Room
   - On remote failure (including a forced refresh), cached repositories return the cached value even past its TTL via `recoverWithCache` — `ClubRepository` only if the cached club is complete — and only surface the error when nothing is cached. `ClubDetailsViewModel`/`MeViewModel` keep on-screen content when a refresh fails and report it through a snackbar instead of an error page
   - "Complete" is meaningful here — e.g. a `Club` cached incidentally from a Member response (missing `members`) is treated as incomplete and triggers a real refresh rather than being served as-is

### Dependency Injection with Koin

All dependency injection is managed through Koin with modular organization:

- **`platformDataModule`** - Platform-specific dependencies (Android/iOS SecureStorage)
- **`coreNetworkModule`** - Supabase client
- **`coreDatabaseModule`** - Room database and DAOs
- **`coreDataModule`** - Services, data sources, repositories
- **`coreAuthModule`** - Auth service and repository
- **`corePresentationModule`** - Shared presentation utilities
- **`authFeatureModule`** - AuthViewModel
- **`clubsFeatureModule`** - Club-related ViewModels and UseCases
- **`booksFeatureModule`** - Books-related ViewModels and UseCases
- **`memberFeatureModule`** - Member-related ViewModels and UseCases

- **`joinFeatureModule`** - JoinViewModel

Koin is initialized in `shared/src/commonMain/kotlin/com/ivangarzab/kluvs/di/KoinHelper.kt`. Follow the `koin-watcher` skill whenever adding a new injectable class or module — it auto-loads on DI-shaped work.

## Navigation Architecture

The app uses a hybrid navigation approach with two layers:

- **App-Level Navigation (Shared):** `AppCoordinator` handles authentication state and determines which major section of the app to show (login vs main app). This logic is shared across Android and iOS.
- **Feature Navigation (Platform-Specific):** Platform NavHost/NavigationStack handles user-driven flows like browsing clubs, viewing details, editing profile, etc.

  - Located in `core/data/src/`
  - Suffixed with `*IntegrationTest.kt`
  - Require local Supabase instance running
  - Excluded from quick test runs via `excludeTests` property

### Test Naming

**Never use commas in backticked test function names** (e.g. `` `deleteClub removes the club, its links` ``). Kotlin/Native rejects them, along with `.` `;` `:` `/` `<` `>` `[` `]` `\`. The JVM accepts them, so Android runs pass and only the iOS compile in CI fails. Before pushing changes to `commonTest`, also run `./gradlew :<module>:compileTestKotlinIosSimulatorArm64 --quiet`.

### Logging

**Always use barK** (`Bark.*`) for all log statements — never `println` or `Log.*`. Follow the `bark-logging` skill for level selection, message formatting, and exception handling rules.
